- [x] **Phase 3: Auth & Token Manager** — done
  - Files created: `src/lib/crypto.ts` (AES-256-GCM token encryption, HMAC-signed OAuth-flow cookie, PKCE verifier/challenge/state generation — shared by tokenManager and auth routes), `src/db/schema.ts` (minimal D1 query helpers: user/account lookup and creation), `src/services/tokenManager.ts` (`getValidAccessToken`/`storeTokens`, 2-min expiry buffer, double-check-before-refresh), `src/middleware/auth.ts` (`getSession`/`requireAuth`/session create-destroy), `src/routes/auth.ts` (`/auth/login`, `/auth/connect-account`, `/auth/callback` — shared callback branches on `purpose: "login" | "connect"` carried in the signed flow cookie). `src/types.ts` extended with `SessionData` and a shared `AppBindings` Hono generic. `src/index.ts` mounts the auth router.
  - **The 3 blocking decisions were resolved and written into `plan.md` §5.2 before coding** (not silently assumed): (1) AES-256-GCM via `TOKEN_ENCRYPTION_KEY`, random IV per encryption. (2) PKCE `state`/`code_verifier` in a signed (HMAC-SHA256, `SESSION_SECRET`), `HttpOnly`/`Secure`/`SameSite=Lax`, 10-minute cookie — not KV, since it's single-browser-scoped and short-lived. (3) KV refresh-race deliberately left unmitigated by a distributed lock — reasoning documented in `plan.md`: Google's refresh tokens are reusable, not single-use, under standard (non-rotating) OAuth client config, so the race's worst case is a wasted API call, not a silent de-auth. `tokenManager.ts` does a cheap double-check-before-refresh to narrow the window. **This rests on an assumption about Google's default token behavior — flagged for verification against the real Google Cloud Console config before relying on it in production.**
  - Verified — real `wrangler dev` boot with locally-generated (fake but correctly-shaped) secrets, not just `tsc`:
    - Crypto primitives unit-tested in isolation first (14 checks: AES-GCM round-trip, random-IV-per-call, wrong-key rejection, HMAC round-trip, **tamper detection** — a modified `purpose`/`tag` payload is rejected, not silently trusted — PKCE verifier length/charset, deterministic challenge, unique state).
    - `GET /auth/login` → 302 to Google with correct PKCE params (`code_challenge`, `S256`, `state`, `prompt=consent`) and sets the signed flow cookie.
    - `GET /auth/connect-account` with no session → redirects to `/auth/login` (`requireAuth` works).
    - `GET /auth/callback` with no `code`/`state` → 400; with `?error=...` → 400 with the message.
    - **Full state round-trip in the running worker** (not just the unit test): correct `state` passes the tamper check and reaches Google's real token endpoint (fails there with `invalid_client`, expected — fake test credentials); a wrong `state` is rejected with 400 *before* any network call.
    - Injected a session record directly into local KV (simulating a completed login) to test the authenticated path without a real Google consent screen: `/auth/connect-account?tag=business` with a valid session correctly proceeds to a new Google redirect (not bounced to `/auth/login`), with `purpose=connect` and `tag=business` correctly embedded in the new signed cookie; an invalid tag is correctly rejected with 400.
  - **Not tested**: an actual successful end-to-end OAuth grant (real Google consent screen, real `code` exchange) — not reachable from this environment without real Google Cloud Console credentials. Everything up to and after that one step is verified; that step itself needs a real manual run before relying on this in production.

## Decisions Made
- Roles finalized as 2-value (`primary`/`secondary`) + required `tag` on secondary accounts (`business`/`side_hustle`/`personal`), single tag per account, label-only (user decision, this session).
- Topology finalized as single-hop fan-out (secondary→primary, primary→every secondary, secondary→every other secondary) — no multi-hop relay needed under the 2-role model.
- Loop guard reverted from per-target origin-comparison back to blanket-skip-of-replicas — the per-target version was correct for the earlier 3-tier hub topology but caused duplicate event delivery under the finalized full-mesh topology (every secondary is always a source). Origin metadata (`originAccountId`/`originEventId`) is retained for provenance and the deletion cascade, not for loop prevention.
- Stray `gemini-code-*` files kept as reference, excluded via `.gitignore` rather than deleted.
- Implementation plan follows `plan.md` §7 phase order unchanged; this file adds concrete file targets and a verification command per phase.

## Errors Encountered
- **Self-caught, this session**: the per-target origin-comparison loop guard (designed to fix the original P0 bug) silently reintroduced a *different* correctness bug — duplicate event delivery — once the role model was generalized to "every secondary is always a sync source." Caught during a deliberate re-trace before any code was written; no implementation impact, but flagging per the pattern: every change to the loop-prevention mechanism needs a full re-trace against the current topology, not just the specific case it was designed to fix.
- **Caught by an independent recheck, not self-caught**: my own Phase 1+2 verification (manual constraint tests, dry-run, real `wrangler dev` boot) all passed, but missed 9 real issues — including the exact same class of duplicate-delivery bug as above, this time in the DB schema instead of the sync algorithm — that a fresh code-reviewer pass with no prior context found. Pattern: my own verification tends to test the specific cases I was already worried about; an independent pass tests things I wasn't looking for. Worth doing a fresh-eyes recheck after each phase that touches correctness-critical logic, not just at the end.
