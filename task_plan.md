## Decisions Made
- Roles finalized as 2-value (`primary`/`secondary`) + required `tag` on secondary accounts (`business`/`side_hustle`/`personal`), single tag per account, label-only (user decision, this session).
- Topology finalized as single-hop fan-out (secondary→primary, primary→every secondary, secondary→every other secondary) — no multi-hop relay needed under the 2-role model.
- Loop guard reverted from per-target origin-comparison back to blanket-skip-of-replicas — the per-target version was correct for the earlier 3-tier hub topology but caused duplicate event delivery under the finalized full-mesh topology (every secondary is always a source). Origin metadata (`originAccountId`/`originEventId`) is retained for provenance and the deletion cascade, not for loop prevention.
- Stray `gemini-code-*` files kept as reference, excluded via `.gitignore` rather than deleted.
- Implementation plan follows `plan.md` §7 phase order unchanged; this file adds concrete file targets and a verification command per phase.

### Incident: unbounded incremental sync of an indefinitely-recurring event (post-production)
With 5 real accounts connected and steady-state syncing cleanly, creating a new weekly-recurring event with no end date (on `side-hustle-3@example-hustle3.test`, already past its first sync) queued **700+ occurrences** expanding out to **August 2040** — Google's internal recurrence-expansion horizon — and had already created 112 real "Busy" replicas across the other 4 calendars before being caught.

**Root cause:** the earlier fix (`timeMax` bound, see "Root-caused further and fixed at the architecture level" above) only protects the *initial* (no-syncToken) fetch. Google's Calendar API rejects `timeMin`/`timeMax` combined with `syncToken` — they're mutually exclusive parameters — so the steady-state **incremental** path (every account, after its first successful sync) has no server-side time bound at all. Creating an indefinitely-recurring event and having it arrive via a normal incremental delta was exactly the case that exposed this; it's not a one-off, it would recur for any account any time this happens.

**Fix (`withinSyncWindow`, `syncEngine.ts`):** every event `fetchEventsDelta` returns is now filtered client-side by the same rolling 30-day window, applied uniformly regardless of which fetch path produced it — this is the real enforcement point, not the `timeMax` request parameter (kept as a courtesy that saves a round trip on the initial fetch, but never relied on alone). Cancellations are exempt from the filter unconditionally — a stale replica needs deleting no matter how far out it would have been; dropping the cancellation here would orphan it forever. Regression test added: an incremental delta containing both a far-future recurring occurrence and a near-term event queues only the near-term one, while a later cancellation of that same far-future event is still processed cleanly.

**Production cleanup performed** (manual, D1 + a live sync trigger, not a code path): purged ~700 stale pre-cancellation queue snapshots (captured before the user cancelled the source event, so they still said `status: confirmed` and would have kept creating junk replicas as they drained) and manually promoted the pending syncToken (safe — it predated the cancellation, so the next fetch using it still correctly returned the cancellation delta). One quirk mid-cleanup: the replica count briefly rose 64→112 before dropping to 0, because an already-in-flight sync run (started just before the purge) finished draining a few more stale entries first — not a new bug, just a timing artifact of manual intervention racing a cron tick. All 112 junk replicas confirmed deleted from D1 (`event_mappings`) after 4 subsequent sync triggers.

**Formerly a known, accepted limitation — now closed, see the daily recurring-series audit section below.** An occurrence of a recurring series more than 30 days out was never queued, and — because incremental syncToken deltas only report *changes*, not a fresh listing — was never queued later either unless the event itself changed again (edit, cancel) or a full re-sync happened (410 recovery, not on a predictable schedule). A long-running unedited recurring series would silently stop replicating past its first ~30 days forever. Originally left as an accepted tradeoff; revisited and fixed after the user pushed on exactly this scenario directly.

**Secondary symptom hit during cleanup — same known cap, different trigger.** Repeatedly clicking "Run sync now" against a queue still holding ~350 mostly-free cancellation entries (no mapping to delete, zero Calendar API budget spent) hit the same 30-second `waitUntil` cap the manual-trigger route has always had — confirmed via Cloudflare's Observability API (`workers/observability/telemetry/query`), which showed `waitUntil() tasks did not complete within the allowed time... and have been cancelled` for that invocation. Not a Calendar-API-budget problem this time (the `CallBudget` never got exhausted) — purely wall-clock: draining hundreds of items sequentially, each needing its own D1 round-trip (`findEventMappingsBySource` + `deleteQueuedEvent`), added up past 30 seconds even with zero external API calls. The stuck `in_progress` row self-heals via the existing 15-minute stale-lock recovery regardless. Resolution: stopped clicking the manual button and let the natural 10-minute cron tick finish the drain instead — cron invocations aren't subject to the `waitUntil` cap (the very first production sync ran cleanly for 257 seconds under cron earlier in this incident history). **Follow-up worth considering, not yet done:** the drain loop's per-item cost model only tracks Calendar API calls; a queue dominated by free D1-only no-ops can still blow the manual-trigger wall-clock budget. If the manual "Run sync now" button needs to reliably handle large backlogs (not just cron), it would need either a D1-operation budget alongside the Calendar-API one, or to stop relying on `waitUntil` for it.

**Tertiary symptom: even cron has a ceiling.** A third, unrelated indefinitely-recurring event (different series ID, `shf9hplffi7iijjg87gtc1hieo`) was also cancelled during this session, and its full cancellation delta (~636 occurrences, expanding out to 2029 — cancellations are deliberately exempt from the 30-day window filter, since a deletion must always propagate regardless of how far out it would have been) landed on the *primary* account's queue in one batch. A single cron invocation ran for over 15 minutes trying to drain it and was killed — confirmed via Cloudflare's documented **hard 15-minute wall-time limit on Cron Triggers** (not the `waitUntil`-specific 30s cap; a different, higher ceiling that applies to cron regardless of `waitUntil`). Same root cause as the secondary symptom above (sequential D1 round-trips per free item add up at large-enough volume), just requiring a much bigger queue to surface. Marked the stuck `in_progress` row `error` manually (same pattern as before) rather than waiting out the 15-minute stale-lock auto-recovery. **Not urgent to fix further**: every cron tick gets its own fresh 15-minute budget, the queue is fully durable (each item is only dequeued after being processed, never lost on a mid-batch kill), and D1-only operations cost nothing on Cloudflare's free tier — so letting the natural 10-minute cron cadence keep chipping away at a very large cancellation batch over several ticks is free, just not instant. Worth revisiting only if this pattern (cancelling a very large indefinitely-recurring series) becomes routine rather than a one-off cleanup artifact — the real fix would be batching the "does this event_id have a mapping" check (currently one D1 query per queue item) into a single bulk query per drain batch.

### Incident: the past-bound gap — `withinSyncWindow` only enforced the future side
Creating a *fifth* recurring event (`6vr33g7h0tpm3gb7on39djs3ui`, weekly, anchored to a start date in October 2025) on the primary account surfaced a mirror-image gap in the fix documented above. `withinSyncWindow` (added to solve the future-side explosion) only checked `startMs <= windowEndMs` — nothing enforced a lower bound. Since incremental (syncToken) deltas have no server-side `timeMin` either, for exactly the same reason they have no `timeMax` (Google rejects both combined with `syncToken`), all 44 of this series' already-elapsed occurrences (Oct 2025 → today) arrived in one delta and were queued and replicated right alongside the legitimately-future ones, directly violating the user's original stated requirement: *"we do not need to sync PAST events unless they are repeating past the current date and time."*

**Fix (`withinSyncWindow`, `syncEngine.ts`):** added a lower bound, `windowStartMs = Date.now()`. Deliberately checks the event's **end** time against that bound, not start — an event that started 10 minutes ago and runs another 50 is still ongoing, not "a past event," and using start would have wrongly excluded it. This also matters for all-day events specifically: Google's date-only `start` parses as that day's midnight UTC, so a same-day all-day event's start already reads as "before now" for any check made after 00:00 — comparing against the (exclusive) end date instead correctly keeps it in scope for its whole day. The future bound stays start-based, unchanged — an event starting 29 days out with a 2-hour duration should count as "within 30 days," not be judged by when it finishes. `timeMin` passed to the initial/full-resync fetch was similarly widened from a static `new Date().toISOString()` to share the exact same `windowStartMs` instant used by the filter, for consistency (both were already computing "now" independently, just not from one shared value).

**Test-suite fallout, fixed properly rather than worked around:** 10 of the 15 existing tests broke immediately, because they used hardcoded absolute event dates (`"2026-08-12T10:00:00Z"`, etc.) written when "today" genuinely was 2026-08-12 — by the time this fix landed, the real calendar date had advanced to 2026-08-13, so those fixtures were now honestly describing past events, and the new lower-bound filter correctly rejected them. This was latent test fragility the fix exposed, not a flaw in the filter — fixed by replacing every hardcoded date across the test file with `hoursFromNow(n)` / `dateDaysFromNow(n)` helpers computed relative to `Date.now()` at test-run time, so the suite can't bit-rot the same way again. New regression test added mirroring the existing far-future one: an incremental delta with both a far-past occurrence and a near-term event queues only the near-term one, and a later cancellation of the far-past event still processes cleanly (cancellations remain exempt from both bounds).

**Production cleanup:** the 46 items already queued under the old (pre-fix) code were stale — queued before the fix deployed, so draining them would have kept creating past-dated junk regardless of the new code, since the window filter only runs at enqueue time, not at drain time. Purged directly (D1-only, safe) without promoting the pending syncToken, so the next sync re-fetched the same underlying delta from Google and this time filtered it correctly. **41 real past-dated "Busy" replicas had already been created** across the other 4 calendars before the fix landed (verified via `event_mappings`); per explicit user decision, left in place rather than bulk-deleted — past-dated events carry no double-booking risk (they're already over) and are considered harmless clutter, not worth the API calls to clean up. Confirmed post-fix: the next sync correctly created only 8 new mappings (2 legitimately in-window occurrences × 4 targets... actually 2 targets for this account pairing), all dated within the 30-day window (Aug 14 – Sept 4), no further past-dated creation.

**Lesson for future window-filter work:** a symmetric bound (past *and* future) needs symmetric enforcement — fixing one side of an unbounded-incremental-sync gap doesn't imply the other side is also covered, since Google's API restriction (`timeMin`/`timeMax` vs `syncToken` mutual exclusivity) applies identically to both directions independently.

### Feature: daily recurring-series audit — closes the "unedited series stops syncing" gap
User pushed directly on the accepted limitation above: *"what happens when an existing recurring event is never updated but we move past the 30 day window?"* Correct challenge — walking through the code confirmed the incremental (syncToken) path never re-reports an event that hasn't changed, so an occurrence that was legitimately outside the window at creation time is **never re-evaluated** once it rolls into the window as "now" advances. A recurring meeting created once and never touched again would have its replication silently stop after ~30 days, permanently — a real failure of the app's core purpose (avoid double-booking), not a cosmetic gap.

**Considered and rejected:** replicating the recurrence rule (RRULE) itself onto target calendars instead of enumerated occurrences — architecturally the "true" fix (Google's own engine would keep it evergreen, no window needed at all), but requires separately fetching the master event (never seen under `singleEvents=true`), detecting and replicating per-occurrence exceptions/EXDATEs as instance-level overrides on the target's own recurring series, and a real data-model change (`event_mappings` would need to go from 1:1-per-occurrence to series-level-plus-exception-overlay). Scoped as a genuine future improvement, not folded into this session.

**Shipped instead — targeted, incremental window-extension, not a full redesign:**
- New table `tracked_recurring_series` (migration `0003`) — `(account_id, recurring_event_id, covered_through)`. Populated automatically the first time the normal 10-minute sync sees an occurrence carrying a `recurringEventId` field (Google stamps this on every expanded instance of a series); `covered_through` initialized to that sync's window edge (`now+30d` at the moment of first sighting) and never touched again by the normal sync path — only the daily audit advances it (verified by a dedicated regression test).
- New `fetchRecurringInstances()` (`googleCalendar.ts`) hitting Google's `events/{id}/instances` endpoint — deliberately not `events.list`: this endpoint takes `timeMin`/`timeMax` directly with **no `syncToken` involved at all**, so none of the mutual-exclusivity restriction that caused this whole class of bug applies to it. The one call in the app that can genuinely ask "what's in this exact date range" without a fight.
- `runDailyRecurringAudit()` (`syncEngine.ts`): for every tracked series whose `covered_through` has fallen behind today's window edge, fetches just the gap `[covered_through, today+30d]` — one day wide in steady state, wider only if a run was ever missed — and enqueues anything new into the *same* `sync_queue` the normal sync already drains, so all the existing budget/resumability/dedup machinery applies for free. Its own small budget (`MAX_DAILY_AUDIT_CALLS = 15`), separate from the main sync's, since both run inside the same `scheduled()` invocation and share that invocation's real subrequest ceiling.
- **No second Cron Trigger** — user's explicit call: Cloudflare accounts have a small fixed cron-trigger budget, not worth spending a second one on this. Instead gated by a KV timestamp (`daily-recurring-audit:last-run-date`, reusing the existing `TOKEN_STORE` namespace) checked inside the existing 10-minute `scheduled()` handler (`index.ts`) — whichever tick is first after UTC midnight runs the audit once, writes the date, the rest of the day's ticks skip it in one cheap KV read.

**Test coverage** (3 new regression tests, 19 total): a tracked series with a stale `covered_through` gets its new occurrence enqueued and, on the very next normal sync, actually replicated (full round trip, not just "was queued"); a series already caught up makes no API call for itself; a normal sync re-seeing an already-tracked series never resets its `covered_through` backward. One test-isolation wrinkle surfaced and fixed along the way: D1 state persists across tests in the file, so a "should make zero calls" assertion needs scoping to the test's own series, not "zero calls at all" — otherwise a previous test's still-in-window tracked series (a real, correct outcome — `covered_through` is *supposed* to trail the ever-advancing window edge by the elapsed-time-since-last-check) trips a false failure.

**Known limitation, not retroactive:** only series the app sees *after* this feature deployed get tracked — a recurring series fully synced before this shipped won't be tracked (and so won't get the daily-audit safety net) until it's next touched (edited/cancelled, generating a fresh incremental delta) or a 410 forces a full re-sync. Acceptable: affects only the small set of recurring series that existed before this deploy and are never touched again, the exact narrow case this feature closes for everything going forward.

### Incident: same-day window-widen deploy left already-tracked recurring series stuck between the old and new edge
User noticed events sitting in the newly-exposed 30–42 day gap for a recurring series weren't appearing, minutes after the 42-day deploy. Root-caused via D1, not guesswork: `tracked_recurring_series` showed the mechanism directly — series `5dr5rsjimtfk07k079c4bs3i9d` was tracked at `01:10:55` with `covered_through = 2026-09-12` (30-day math), while series `20l37n4dkn8n99vki0a42e58hq` was tracked at `01:21:03` — after the 42-day deploy landed — with `covered_through = 2026-09-24` (42-day math). Cross-referencing `sync_logs`, the `01:10:51` scheduled run was also the first tick of the day, meaning `maybeRunDailyAudit`'s KV gate (`daily-recurring-audit:last-run-date`) got set to today's date **before** the deploy, using the old 30-day code. Every tick since (`01:20` through `02:20`) correctly saw the gate already set for today and skipped re-running the audit — it has no way to know the code changed mid-day. So `5dr5r`'s gap between the old edge (Sep 12) and the new one (Sep 24) sat unaudited, and wouldn't have been checked until the next UTC-day rollover.

**Not a design flaw in steady state** — the once-per-UTC-day gate is exactly correct behavior for its actual purpose (don't burn API calls re-auditing the same day's window edge repeatedly). This is specifically a same-day-deploy-changes-the-window-size interaction, a rare event by nature (window size doesn't change often). **Fix applied: `wrangler kv key delete` on the gate key**, forcing the next tick's `maybeRunDailyAudit` to run again today under the now-current 42-day code, picking up every tracked series' gap in one pass rather than waiting until tomorrow. Deliberately a manual, one-time operational action rather than new code — engineering a permanent mechanism (e.g., versioning the KV key by `FUTURE_WINDOW_MS`'s value, so a changed window size invalidates the day's gate) would add real complexity for a situation expected to recur only on the rare day someone changes this specific constant.

**Separate, pre-existing structural gap this incident surfaced but didn't cause:** the daily audit only ever covers *recurring* series (via `tracked_recurring_series`) — a plain one-off (non-recurring) event that Google's incremental delta already "delivered and rejected" under the old window has no equivalent safety net at all. It would only get picked up if the event changes again (generating a fresh delta) or a token expires and forces a full re-sync. This was already true before the 42-day change (any one-off event near the old boundary carried the same latent risk) and isn't something widening the window fixes or worsens — noted here because this incident is what made it visible, not because it's new.
